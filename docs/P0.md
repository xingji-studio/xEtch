# P0 技术验证记录

验证日期：2026-11-14。状态：**Windows 原生与 Linux 基础 P0 验证通过；macOS 实机及发布验收仍待完成**。

## 可重现实验

运行 `python3 scripts/p0_validate.py --output artifacts/p0.json`。脚本仅创建临时测试镜像，结束后清理；所有子进程均无需 root 和内核挂载。实测结果保存在 [p0-linux-results.json](p0-linux-results.json)。

Linux 环境：WSL2 Linux x86_64、QEMU 8.2.2、Rust 1.96.0。

Windows 环境：Windows 11 x64（10.0.26200.8457）、原生 Rust 1.95.0 / MSVC、Windows SDK 10.0.26100.0，QEMU 11.1.0 的项目内 UTF-8 清单配置。通过 WSL 启动原生 `cargo.exe`、`xetch.exe` 与 QEMU `.exe`，磁盘操作在 Windows 进程内执行；不是使用 Linux 后端代替 Windows 验收。

| 实验 | 结果 |
| --- | --- |
| FAT32 离线创建、写文件、fsck 检查 | 通过 |
| monolithicSparse / monolithicFlat / twoGbMaxExtentSparse / twoGbMaxExtentFlat / streamOptimized，经 NBD 读取 | 五项通过 |
| 对以上每种 VMDK 建立 QCOW2 覆盖层，随机写块、FLUSH、重开读取、导出 VMDK | 五项通过 |
| 写入前后对源描述文件和所有 extent 文件做 SHA-256 比对 | 保持不变 |
| 5 GiB 稀疏分卷、跨 2 GiB 边界与超过 4 GiB 偏移 | 通过 |
| ext4：debugfs 写入、读回，e2fsck 检查 | 通过；只证明 Linux 工具路径可行 |
| NTFS：ntfscp 写入、ntfscat 读回 | 通过；只证明 Linux 工具路径可行 |

另增加了 5 GiB 稀疏分卷 VMDK：验证 2 GiB extent 边界两侧以及超过 4 GiB 的偏移写入，刷盘导出后读回并比对源文件未变。真实 VMware 来源的复杂大镜像仍待覆盖。测试中的随机块写入针对临时样本；产品 CLI 尚未开放原始扇区写入。

## Windows P0

[Windows 运行记录](p0-windows-results.json) 包含 12 项通过的检查：本机依赖、MBR/GPT、五种 VMDK 子格式、中文与空格宿主路径、失败修改与输出冲突、JSON-RPC、5 GiB 分卷及 64 位偏移。

`scripts/windows_validate.ps1` 用独立进程重开会话、导出并读取文件，对源描述文件和 extent 的哈希进行比对。`scripts/windows_common.ps1` 明确使用 UTF-8 stdin/stdout，兼容 PowerShell 5.1。普通 QEMU 发行包暴露了两层编码问题：命令行 JSON 与 ANSI 文件打开接口。后端使用 ASCII JSON 转义；准备脚本为项目内 QEMU 副本加入 UTF-8 进程清单。原安装包 SHA-512 和修改前后工具 SHA-256 均在运行记录中保留，机器级区域设置未改变。

该配置通过现有 Windows SDK `mt.exe` 实现，不运行 QEMU 安装程序，不修改已安装软件。它是开发/测试依赖配置，完整发布包、签名及第三方交付材料仍待完成。依据为 [Microsoft UTF-8 进程清单文档](https://learn.microsoft.com/en-us/windows/apps/design/globalizing/use-utf8-code-page)；已验证的 QEMU 原始包来自其[官方下载页](https://www.qemu.org/download/)指向的 [Windows 分发站点](https://qemu.weilnetz.de/w64/)。

## 新文件系统适配

使用固定版本 `fstool 0.5.0` 原生 Rust 适配器，读取无需操作系统挂载或 Linux 工具。写入仍在子覆盖层中进行。

| 文件系统 | 当前产品能力 | 验收 |
| --- | --- | --- |
| exFAT | 浏览/导出；实验性新增、覆盖、目录创建、删除、文件/目录改名与移动；none/MBR/GPT 格式化 | Windows 与 Linux 通过；完整 Unicode 映射、连续分配、`exfatprogs` 独立检查通过 |
| ext4 | 浏览/导出；实验性新增、覆盖、目录创建、删除、文件/目录改名与移动；none/MBR/GPT 格式化 | Windows 与 Linux 通过；权限/硬链接/ACL/扩展属性保留、默认 ACL/setgid 继承、索引目录、`e2fsck` 和 `debugfs` 校验通过 |
| NTFS | 浏览/导出；NTFS-3G 2026.9.28 可选普通文件写入 | Windows 与 Linux 原生验证；独立 ACL/ADS/EA/MFT、回退和卷状态检查通过，见专门报告 |

运行记录：[Linux 文件系统检查](filesystems-linux-results.json)、[Windows 原生文件系统检查](filesystems-windows-results.json)、[Windows 输出的独立检查](windows-exports-check-results.json)。后者明确由 Linux 工具检查 Windows 产生的字节，不代替 Windows 运行证据。

早期 fstool NTFS 原型可新增普通文件，但独立 `mkntfs` 镜像的覆盖写入被其 `non-LFS-shaped $LogFile` 检查拒绝。因此未在产品中启用这一候选写入器，也未通过删除重建规避。现在由独立 NTFS-3G 工作进程接管写入，继续复用分区窗口和 QCOW2 事务。

可用 `cargo run --release -p xetch-core --example ntfs_write_probe -- artifacts/fs-fixtures/ntfs.img` 独立复现：探针仅在临时完整副本上调用候选库的覆盖写接口，输入不被修改。[Linux 证据](ntfs-candidate-linux.json)与 [Windows 原生证据](ntfs-candidate-windows.json)记录其拒绝原因。另核对了 0.5.4 源码，仍有同一 `$LogFile` 检查，因此没有仅通过升级版本宣称问题已解决；该版本也将 Rust 最低要求提高到 1.95。

exFAT/ext4 的写入与格式化均为实验能力。[Linux](extended-linux-results.json) 与 [Windows 原生](extended-windows-results.json)扩展矩阵各含 exFAT 12 组、ext4 12 组检查及三种 exFAT 新建布局。检查覆盖带内容目录移动、NoFatChain 文件/目录、大小写、现有元数据保留、默认 ACL/setgid 继承、属性块损坏拒绝、ENOSPC 回退及日志待恢复拒绝。失败操作不会推进工作区 head；尚未声称覆盖所有特性、元数据组合、异常镜像或断电恢复。具体限制见 [exFAT/ext4 说明](EXFAT-EXT4.md)。

新建矩阵的 [Linux](format-linux-results.json)与 [Windows 原生](format-windows-results.json)各通过 16 个场景，覆盖 exFAT/ext4 的三种布局、直接新建 VMDK、微小尾部块组、多块组和 5 GiB 稀疏 VMDK。分别检查新建、编辑和删除后的输出，独立校验分区类型、两份 GPT、卷标识、日志和备用超级块；新建失败不残留输出。

## NTFS 与 Windows GUI

[NTFS 选型与验证](NTFS.md)记录更成熟组件的取舍，最终固定 NTFS-3G 2026.9.28。使用自定义块设备回调的用户态库，不加载 FUSE、Windows 内核驱动或挂载宿主卷；Windows 工作进程是 MinGW 构建的原生 x64 PE，仅依赖系统 DLL。NTFS 元数据、日志和权限算法沿用上游，移植仅补齐宿主兼容接口。

[Linux 结果](ntfs-linux-results.json)和[Windows 原生结果](ntfs-windows-results.json)各通过 14 项检查，包括普通文件覆盖的驻留/非驻留转换、中文/非 BMP 路径、目录与文件操作、原 ACL/ADS/EA 和 MFT 身份保留、IMG/VMDK 互操作、ENOSPC/冲突回退、写入扇区后工作进程退出回退、缺失组件的只读降级、脏卷/休眠卷/损坏日志拒绝。启用大容量检查另测 5 GiB NTFS 卷；仍未声明大于 4 GiB 的单个文件已通过。

首版 WinUI 3 GUI 已构建并启动。测试变体在真实窗口中执行同一控制器，经过 JSON-RPC 完成 NTFS 浏览和编辑、文件及镜像导出、会话恢复、错误显示和按钮状态检查，实际 XAML 视觉树可渲染成 PNG；[运行记录](windows-gui-results.json)保存 11 项检查。GUI 生成的 IMG 另经 ntfsfix -n 和 ntfscat 独立检查。因电脑控制工具的 WSL 路径初始化错误，未完成文件选择器及鼠标键盘交互自动验收。GUI 构建和测试见 [Windows 前端说明](../apps/windows/README.md)。

GUI 已扩展 exFAT 改名和新建卷选择，并完成 [exFAT](windows-gui-exfat-results.json)、[ext4](windows-gui-ext4-results.json)各 14 项原生控制器/窗口检查，覆盖实验开关、会话恢复和错误回退；选择器及输入验收边界同上。

新建对话框已加入 ext4，与 CLI 共用 `image.create`。新建 [ext4](windows-gui-create-ext4-results.json)与 [exFAT](windows-gui-create-exfat-results.json)各通过 18 项实际窗口/控制器检查，并独立验证新建和另存的镜像；文件选择器和输入交互仍未自动验收。

## 形成的实现决策

1. Rust 应用核心通过用户态 NBD 与 QEMU Storage Daemon 通信。QMP 暂不需要，后续后台作业可以在此基础上增加。
2. QEMU 只作为子进程，通过参数数组启动，不经过 shell。显式指定文件协议与镜像格式，监听仅绑定 127.0.0.1，使用随机导出名。
3. 修改工作区用 QCOW2 支持包括 streamOptimized 在内的源镜像，不直接修改 VMDK 子格式元数据。输出先限制为 raw / monolithicSparse。
4. FAT 使用 `fatfs 0.3.6`；exFAT/ext4 使用 `fstool 0.5.0` 用户态实现接入同一个分区窗口。文件系统依赖只启用所需特性。
5. NTFS 原生 Rust 读取与独立 NTFS-3G 写入共用同一事务机制。Linux 文件系统工具仅生成独立样本和检查结果，没有被当作跨平台产品后端。
